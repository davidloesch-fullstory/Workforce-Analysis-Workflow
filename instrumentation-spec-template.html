What this document is. A pre-flight configuration plan. It tells a FullStory admin exactly which pages, named elements, defined events, and custom properties to set up for a target tool before a workforce automation analysis runs. Configuring these promotes the tool's signal from low-precision URL-path inference to high-precision, action-level events.

How it fits the analysis

Three parties, one loop. FullStory SE produces the spec, a FullStory admin configures it, and the analysis later consumes the new signals.

6How to Configure in FullStory

The admin handoff. All of this is no-code via Data Studio (Data Management). Order matters: pages → elements → events that reference them.

1Define Pages Verified vs docs
Go to Settings > Data Management > Pages → Create Page. Add each page from Section 2 using URL rules. Paste a real instance URL into the search box first to check for conflicts (rules are mutually exclusive).
Source: FullStory — Pages
2Name Elements Verified vs docs
Open a recorded {tool_name} session → Page Insights > Inspect Mode → click the control → name it in Data Studio. Repeat per surface where agents work in more than one. The name maps to a CSS selector (element_definition_id).
Source: FullStory — Data Studio · Element Definitions
3Define Events Verified vs docs
In Settings > Data Management > Events → Create Event (or "Define event" from Inspect Mode / the event builder). Compose each event from Section 4 by referencing the named element plus page scope, and attach the Section 5 properties.
Source: FullStory — Define Events
Then let it capture. Allow ~2–4 weeks of data accumulation before the analysis so volumes are meaningful. After that, the workforce analysis discovers these by name (discover_org_context) and builds metrics directly on them — promoting them from "enrichment" to primary signal.

How the rollup is used. Start the analysis with the spec'd tool(s) for high-precision signal; "future tool spec" rows mark where URL-path fallback is still the only signal, so findings there stay directional until those tools are instrumented. Each future tool gets its own tab (same structure) in a later pass.

Dedup & double-count guardrails

  • One workflow = one canonical event source. Where two tools touch the same workflow, the rollup names the canonical owner to avoid summing both.
  • Cross-tool handoffs are modeled as a single "linkage" event, not two independent creations.
  • Active-time per tool stays a directional floor, never summed across overlapping tabs.
